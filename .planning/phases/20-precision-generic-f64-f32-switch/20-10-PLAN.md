<objective>
GAP 2 closure (PREC-05) — kernel + math hardening. The f32 oracle gate (`f32_parity.rs`) passes only for base-family SCALAR cases. Code review CR-01 + CR-02 document an unsound staging buffer length contract that silently returns WRONG f32 values for multi-component / spinor / f12-derivative outputs (where the true output element count exceeds the per-chunk f64 allotment). This plan fixes the CRITICAL defects (CR-01, CR-02) AND the adjacent f32-correctness warnings (WR-01, WR-03, WR-04, WR-05, WR-06). The dependent oracle tests that prove the fixes land in Plan 20-11 (next wave).

Purpose: make the f32 compute path actually correct for the cases the current tests do not cover. The dominant threat is silent data corruption — wrong f32 values returned as if correct. These fixes bound every f32 write/scan to the true output region and make the math layer's f32 intermediates honor the documented "all intermediates stay f64" contract.

Output: CR-01 fixed in all 7 kernel files; CR-02 + WR-01 fixed in f12.rs; WR-03 in pdata.rs; WR-04 across stg/pdata/rys/boys; WR-05 in boys.rs (host + #[cube]); WR-06 in all 7 kernels. The f64 path stays byte-identical (PREC-04).

KEY DATA-FLOW FACT (verified 2026-05-21, drives every CR-01/CR-02 fix): the facade allocates `chunk_staging: Vec<f64>` sized to `chunk_len` = the TRUE per-chunk output element count (api.rs:269-277), passed as `&mut [f64]` through `io.staging_output()` (dispatch.rs:137) and `kernels::launch_family` (executor.rs:243-244) to each outer dispatcher. So on the F64 arm `staging.len() == out_elems`; on the F32 arm, AFTER `bytemuck::cast_slice_mut`, `staging_f32.len() == out_elems * 2`. Therefore the TRUE output element count is exactly the f64 `staging.len()` captured BEFORE the cast: `let out_elems = staging.len();` in the outer dispatcher (the f64 slice length), then pass `&mut staging_f32[..out_elems]` to the typed inner.
</objective>
