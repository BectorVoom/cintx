# Phase 19 Plan 06: Scalar ECP Byte-Identity Close Summary

**Replaced the 19-04 numerical-quadrature `compute_type1_pair`/`compute_type2_pair` with verbatim Rust ports of PySCF nr_ecp's `ECPtype1_cart` / `ECPtype2_cart` drivers — the level-adaptive Gauss-Chebyshev convergence loop, the 19-05 K-Taylor radial assemblers, and the per-(li, lj, l_c) angular splice — reaching `atol=1e-12, rtol=0.0` byte-identity vs vendored PySCF nr_ecp (worst-case `|diff| ≈ 1.4e-14`) and flipping the two scalar manifest rows to `oracle_covered=true`.**

## Output items requested by the plan

- **Worst-case |diff| observed:** `≈ 1.42e-14` for both cart (576 elements, 24×24 AO) and sph (484 elements, 22×22 AO) — three orders of magnitude inside `atol=1e-12`.
- **Kernel-level corrections required during iteration:** **None.** The verbatim driver port passed byte-identity on the first run after Task 1. No sign-convention, normalization, angular-splice-index, or cart-vs-sph-transform fixes were needed during iteration — the careful pre-implementation read of `ECPtype1_cart` / `ECPtype2_cart` and the helper round-trip (`CINTc2s_bra_sph` + `CINTs2c_bra_sph` ⇒ `omega ← M^T M omega`) landed correct. The two-`dgemm` Type-2 angular splice (`dgemm_(N,N)` then `dgemm_(T,N)` with `common_fac` scaling, writing F-order `gctr[c_off + col*di + row]`) was transcribed directly from the column-major C layout.
- **rs-grid reuse of `gauss_chebyshev_nodes_weights_host`:** The runtime `ECPgauss_chebyshev` formula (`gauss_chebyshev_nodes_weights_host(LEVEL_MAX=11)`) matches PySCF's embedded `rs/ws_gauss_chebyshev2047` static table to `~7e-15`; the adaptive loop sub-samples it via `rs[start + n*step]` exactly as the C does. No grid adjustment was needed — the converged radial integral is insensitive to the sub-ULP grid difference at `atol=1e-12`.
- **Manifest-flip mechanics used:** **lock-edit + build.rs regenerate** (per 19-01: the lock JSON is canonical, `build.rs` regenerates `api_manifest.{csv,rs}` on every build). Set `oracle_covered=true` on the two scalar entries in `compiled_manifest.lock.json`, rebuilt `cintx-ops`, verified the CSV/rs flipped, then ran `manifest-audit` (zero diff, exit 0). The `oracle-covered-update` xtask subcommand was NOT used (it only stamps symbols present in `generate_profile_parity_report`, and ECP parity is a standalone test file).

## Deviations from Plan

None affecting correctness or scope. Two notes:

### Note 1 — `manifest-audit --check-lock` (the milestone oracle-coverage gate) still fails by design

The plan's verify gate is the plain `cargo run -p xtask -- manifest-audit` (exit 0, zero diff — confirmed). The stricter `--check-lock` variant additionally runs `check_oracle_coverage`, which fails while ANY stable entry is `oracle_covered=false`. Before this plan it reported **4** uncovered stable ECP entries; after this plan it reports **2** (the `ipnuc_{cart,sph}` rows, which the plan explicitly keeps `false` for 19-07). This is a strict improvement and exactly the planned intermediate state — the milestone-level `--check-lock` gate fully closes once 19-07 lands the gradient and flips the last two rows. Not a regression; not a deviation from the plan's literal verify command.

### Note 2 — host-only kernel (D-16, plan-sanctioned)

`ecp_type1_cart` / `ecp_type2_cart` and all angular helpers are pure host Rust with no `#[cube]` body — the D-16 host-first decision and a documented CLAUDE.md ("CubeCL is the primary compute backend") deviation tracked in 19-CONTEXT.md "Deferred Ideas". The byte-identity gate runs CPU-vs-C on `--features cpu`, so the host port closes the requirement; the `#[cube]` GPU counterpart is deferred. Documented in the `kernels/ecp.rs` file rustdoc "CubeCL constraint deviation" section.
