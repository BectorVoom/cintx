# 30-01c Debug: rank-9 sa01 byte-identity blocker — ROOT-CAUSED & FIXED

## TL;DR (the actual bug)

The `cg_sa10sa01` / `giao_sa10sa01` dispatch arms in
`crates/cintx-cubecl/src/kernels/sigma_1e.rs` **hardcoded the rinv center as
`[0.0, 0.0, 0.0]`** (comment: *"rinv center = PTR_RINV_ORIG default [0,0,0]"*)
instead of reading `env[PTR_RINV_ORIG]`. Vendor libcint evaluates these families at
the single rinv center `env[PTR_RINV_ORIG]` (intor3.c `int1e_type=1`, charge +1).
The Phase-30 fixture sets `env[PTR_RINV_ORIG] = [0.30, -0.45, 0.60]` (a NON-zero
center), so cintx computed the integral at the wrong operator center → wrong values.
The symptom (structural zeros at component slots) was the symmetric-center `[0,0,0]`
zeroing contributions the off-center vendor result keeps.

**Both prior hypotheses were WRONG:**
- The 30-01c-SUMMARY blamed the *gout → gc-block layout / c2s transform*. **Disproven.**
- This DEBUG (earlier revision) blamed the *g-tensor assembly* (`sa01_g1_bothside` /
  `sa01_x1i_of_g1` / HRR headroom). **Disproven.**

Both the g-tensor AND the `cart_to_spinor_si_2d` transform are byte-correct. The bug
was a one-value plumbing omission, invisible to every controlled test because those
fixtures set `PTR_RINV_ORIG = [0,0,0]`, which happened to match the hardcode.

## The fix

1. `crates/cintx-cubecl/src/kernels/sigma_1e.rs` — added a `rinv_orig: [f64;3]`
   parameter to `launch_int1e_giao_sigma_family_spinor_pair`; both sa01 arms now pass
   `rinv_orig` (not `[0,0,0]`) to `launch_int1e_sa10sa01_spinor_pair`.
2. `crates/cintx-compat/src/raw.rs` — added `int1e_cg_sa10sa01_` / `int1e_giao_sa10sa01_`
   to `is_giao_rinv_center_symbol` so the plan extracts `rinv_orig` from
   `env[PTR_RINV_ORIG]` (the nucsp arms still use atom-summed `origin_coords/charges`).
3. Test collectors (`giao_sigma_1e_parity.rs`) now read `env[PTR_RINV_ORIG]` and pass it.

After the fix: the 3 `#[ignore]`d gates (`giao_sigma_1e_cg_sa10sa01`,
`giao_sigma_1e_giao_sa10sa01`, `giao_sigma_1e_sa10sa01_cg_giao_collapse`) are GREEN,
`test_no_silent_skip` asserts sa01 byte-identity, and `oracle_covered=true` for both
sa01 rows in `compiled_manifest.lock.json` (mirrors auto-regenerated by
`cintx-ops/build.rs`).

## How it was found — the cart-path discriminator (the "DECISIVE NEXT EXPERIMENT")

Implemented exactly as this DEBUG's prior revision prescribed, plus systematic
bisection. Harness lives in `crates/cintx-oracle/tests/sa01_cart_discriminator.rs`
(+ `vendor_int1e_cg_sa10sa01_cart` FFI shim in `vendor_ffi.rs`, build.rs allowlist,
and the `sa01_cart_gc_for_test` debug accessor in `sigma_p.rs`).

Evidence chain (all vendor byte-identity, atol ≤ 1e-9):

| Experiment | Result | Conclusion |
|-----------|--------|------------|
| cart `gc` vs `vendor_int1e_cg_sa10sa01_cart` (s×s, p×s, p×d) | match, max\|dev\| ≤ 1.3e-12, 0 struct diffs, abs scale identical | g-tensor BYTE-CORRECT |
| nctr=2 / nprim=3 gc per-ci linearity | max dev 0.0 | general-contraction gc BYTE-CORRECT |
| full spinor path, nctr=1 (PTR_RINV_ORIG=0) | 0/108 vs vendor | transform `cart_to_spinor_si_2d` BYTE-CORRECT |
| full spinor path, nctr=2 controlled (PTR_RINV_ORIG=0) | 0/432 | nctr/scatter BYTE-CORRECT |
| real fixture (PTR_RINV_ORIG=[0.3,-0.45,0.6]) via dispatcher | broken (groups 0,1,2 half-zero) | ← the failure |
| real fixture, launcher called directly with rinv=env[PTR_RINV_ORIG] | **0/432** | ✅ ROOT CAUSE CONFIRMED |

Why the cart buffer looked correct: the cart driver also reads `env[PTR_RINV_ORIG]`,
so its output was right. The rinv value only enters through env — which the cart path
honored and the spinor *dispatch arm* silently dropped.

## Lesson for new families

Always add a fixture with a NON-zero `env[PTR_RINV_ORIG]` for any rinv-center family.
A `[0,0,0]` center is symmetric and masks a dropped/ignored rinv plumbing — the same
class as the nctr>1 and non-square-block masking pitfalls.
