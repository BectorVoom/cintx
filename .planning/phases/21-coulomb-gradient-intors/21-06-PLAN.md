Repair the `int3c2e_ip1` family (Risk R1, family 0): replace the operator-blind scalar stub in `launch_center_3c2e_typed` with a real 3-component derivative kernel (same `gout_ip1` reuse, preserving the 3c2e Pitfall-4 kl mapping), and FLIP the oracle reference from the plain `vendor_int3c2e_{cart,sph}` to the derivative `vendor_int3c2e_ip1_{cart,sph}`. Purpose: This is the most important correctness fix in the phase. `center_3c2e.rs::launch_center_3c2e_typed` is operator-blind, scalar-output, no derivative — it silently returns the PLAIN (non-derivative) integral for `int3c2e_ip1`. The bug is latent and verified: the oracle "passes" today ONLY because the existing tests reference plain `vendor_int3c2e_*` (see the explicit comments at safe_api_arity3_parity.rs:10-23,443-444 and center_3c2e_parity.rs). But pyscf_rs's DF-gradient runtime (pyscf-grad/src/hooks.rs:24) consumes `int3c2e_ip1` as a DERIVATIVE — so today it gets a silently-wrong scalar. This plan ships the real derivative kernel and flips the oracle to the real reference, closing the silent-wrong runtime path.

Output: the `ip1` derivative branch in `launch_center_3c2e_typed` (depends on 21-05 exposing `gout_ip1`/`F12Shape` as `pub(crate)`); the `vendor_int3c2e_ip1_sph` FFI wrapper (the `_cart` wrapper exists at vendor_ffi.rs:552); the flipped oracle references in `center_3c2e_parity.rs` + `safe_api_arity3_parity.rs`.
